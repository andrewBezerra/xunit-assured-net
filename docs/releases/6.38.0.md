New in XUnitAssured.Camunda: what a test generated from a scenario needs to run the customer's process on Camunda, with the steps it calls for real. Upgrading from 6.37.1 requires no code changes, and nothing that works today behaves differently.

- **A mock that computes its answer.** `MockJobWorker(type).ThenCompleteWith(job => ...)` completes the job with what a function returns, from the job (`JobKey`, `JobType`, `ElementId`, `ProcessInstanceKey`) and the instance's variables (`Variables`, by name, as JSON). It is where a test runs what the worker would do, such as calling an API or producing to a topic, and completes the job with what came back. `MockMessage(name).ThenCorrelateWith(message => ...)` does the same for a message, from the subscription that waits for it (`MessageName`, `CorrelationKey`, `ElementId`) and the variables of the instance that waits. The function is asynchronous, runs once per job or subscription, and gets a cancellation token that stops with the mocks.
- **A function that throws fails the test, saying why.** The job fails with no retries, so Camunda opens an incident instead of waiting for a worker that will never answer, and the message is left uncorrelated. The next assertion fails, and its message names the job or the message and the exception.
- **The variables are the process-scope ones**, as Camunda's search shows them when the job or the subscription appears. The search reads the secondary storage, and may truncate a very large value; a value that is no longer JSON comes as its text.
- **A required cluster.** `CamundaSettings.LoadRequired()`, and the `RequiredCamundaClusterFixture` built on it, read the `camunda` section like `Load()`, but fail when there is no cluster address: no `restAddress` in the section and no `CAMUNDA_REST_ADDRESS` (or `ZEEBE_REST_ADDRESS`). The message says what to add. It is for a test that only makes sense on a real cluster, such as one a generator writes; a chain without this fixture still falls back to `http://localhost:8080`, as in 6.37.0.
- **The path the instance took.** `AssertElementCompleted(elementId, times)` asserts how many times an element completed in the instance: it waits for the count, gives up at once when it goes past, and with fewer completions fails when the instance has ended. With 0, it waits for the instance to end. `AssertEndedAt(endEventId)` asserts that the instance completed through that end event: it gives up at once when the instance completed through another one (and names it), was terminated, or has an open incident.
- The new verbs are named `ThenCompleteWith` and `ThenCorrelateWith`, and not overloads of `ThenComplete` and `ThenCorrelate`, so a call that passes `null` today still compiles.
