New in XUnitAssured.Camunda.Testcontainers: **`CamundaFixture`**, which runs the test either on the Camunda and the customer's workers in Docker, or on a cluster of your own, as `testsettings.json` says. Upgrading from 6.38.0 requires no code changes, but **the Camunda that `CamundaContainerFixture` starts now speaks only https**: a test that called its address on its own, outside the chains, has to trust `Settings.CaCertificatePath`.

- **The workers and what they depend on, declared in `camunda.containers`.** Each entry of `services` has the `name` other containers reach it by, the `image`, the `environment`, the `ports` the test reaches from the host, a `wait` (a `port`, a `path` that answers with success on that port, or a `log` line) and a `dependsOn`. The fixture creates one network, starts `camunda/camunda` on it as `camunda`, and then the list in `dependsOn` order, each ready before the next, keeping the written order otherwise. A cycle, an unknown dependency, a repeated name, a container named `camunda` or one without an image fails when the fixture is created, naming what is wrong.
- **Every container gets the Camunda's address on the network** as the SDK variables: `CAMUNDA_REST_ADDRESS` and `ZEEBE_REST_ADDRESS` (`http://camunda:8080`) and `ZEEBE_GRPC_ADDRESS` (`http://camunda:26500`), with `CAMUNDA_AUTH_STRATEGY`. A worker that reads other names uses placeholders in its `environment`: `${camunda.restAddress}`, `${camunda.grpcAddress}`, `${camunda.username}`, `${camunda.password}`, `${<name>.host}` and `${<name>.port:<port>}`. A variable written in the list wins over the fixture's; an unknown placeholder fails with its name.
- **The Camunda in Docker speaks only TLS, on REST and gRPC, with both fixtures.** On every run the fixture generates, with .NET alone, a test certificate authority and a server certificate for `camunda` (its name on the network), `localhost`, `127.0.0.1` and `::1` (and the Docker host in `TESTCONTAINERS_HOST_OVERRIDE` or `DOCKER_HOST`), valid for a day. The certificate and its key go into the container at `/xunitassured/tls`, and the Camunda turns TLS on with Spring Boot's `SERVER_SSL_ENABLED`, `SERVER_SSL_CERTIFICATE` and `SERVER_SSL_CERTIFICATE_PRIVATE_KEY` for REST and with `CAMUNDA_API_GRPC_SSL_ENABLED`, `CAMUNDA_API_GRPC_SSL_CERTIFICATE` and `CAMUNDA_API_GRPC_SSL_CERTIFICATEPRIVATEKEY` for the gRPC gateway. Every address is `https`: `https://camunda:8080` and `https://camunda:26500` on the network, and `https://<docker host>:<mapped port>` for the test. The host copy of the files is deleted when the fixture is disposed.
- **The test's client trusts only that authority.** The new `camunda.caCertificatePath` setting (or `CAMUNDA_MTLS_CA_PATH`) makes `CamundaApiClient` validate the server certificate by that authority alone: the chain has to close at it, the name has to match, and the system's authorities do not count. Both fixtures set it.
- **The workers trust it through the common variables**: `SSL_CERT_FILE` (OpenSSL: Go, .NET on Linux, curl), `NODE_EXTRA_CA_CERTS` (Node), `REQUESTS_CA_BUNDLE` (Python requests), `CAMUNDA_MTLS_CA_PATH` (the Camunda .NET SDK), `ZEEBE_CA_CERTIFICATE_PATH` (the Camunda Java client) and `CAMUNDA_CLIENT_CACERTIFICATEPATH` (the Spring Zeebe `camunda.client.ca-certificate-path`), all pointing at `/xunitassured/tls/ca.pem`; and Java's `JAVA_TOOL_OPTIONS`, with `-Djavax.net.ssl.trustStore` at a PKCS12 truststore the fixture builds, its password new on every run (a declared `JAVA_TOOL_OPTIONS` keeps its options after these). The placeholders `${camunda.caCertificatePath}`, `${camunda.trustStorePath}` and `${camunda.trustStorePassword}` serve a worker that reads other names.
- **Two authentication modes, in `camunda.containers.authentication`.** `basic`, the default: the Camunda asks for a `xunit` user with a new password on every run, the workers get them in `CAMUNDA_BASIC_AUTH_USERNAME` and `CAMUNDA_BASIC_AUTH_PASSWORD`, and the test's own client uses the same. `none`: the API is open, the workers get `CAMUNDA_AUTH_STRATEGY=NONE`, and the client sends no credential. `oauth`, with a Keycloak the fixture starts and configures, comes in 6.40.0; asking for it now fails with that message.
- **Where the test runs.** With `camunda.containers`, the containers. Without it and with `camunda.restAddress` (or `CAMUNDA_REST_ADDRESS`), that cluster. With neither, the fixture fails when it is created, with the message of `CamundaSettings.LoadRequired()` and the containers as the other way: the test does not fall back to localhost.
- **A container that fails to start** stops the ones already started and the network; disposing the fixture stops them in reverse order, then the network.
