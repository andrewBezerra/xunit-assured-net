New in XUnitAssured.Camunda.Testcontainers: **`camunda.containers.authentication: "oauth"`**. The `CamundaFixture` starts a Keycloak next to the Camunda, builds the realm by itself, and the customer's workers and the test get their token from it, the way they do against a self-managed Camunda with Identity. Upgrading from 6.40.0 requires no code changes.

- **The customer only names the worker's client.** In `camunda.containers.oauth`, `clientId` is the client id the worker uses with client credentials; `clientSecret` is optional (without it, the fixture generates one on every run and hands it to the worker); `audience` is optional too, `orchestration-api` by default, the one of a self-managed Camunda. A missing `clientId` fails when the fixture is created, saying what to add.
- **A Keycloak like the self-managed one.** The image is `camunda/keycloak:quay-26.6.4`, with the `/auth` path and the `camunda-platform` realm, on the network as `keycloak`, **over https only**, with the same test-authority certificate as the Camunda (the certificate now also names `keycloak`). `KC_HOSTNAME` fixes the issuer at `https://keycloak:8443/auth/realms/camunda-platform`, so a token asked from the host (the test, on the mapped port) and one asked from the network (the workers) carry the same `iss`.
- **The realm is imported from a file the fixture writes,** and not built through the admin API: `start-dev --import-realm`, ready when the realm publishes its OpenID configuration. No step after start-up, and no admin password. It has three confidential clients: `camunda` (the Camunda's own, for its web login), the worker's and `xunitassured-test`, the test's. The worker's and the test's use client credentials (a service account), with an audience mapper for the Camunda's audience and a `client_id` claim, which the Camunda reads to know who calls.
- **The Camunda validates the token by that Keycloak,** through `camunda.security.authentication.method=oidc` and `camunda.security.authentication.oidc.*` (the issuer, the token, JWKS and authorization endpoints, the client, the audience, `client_id` as the client-id claim and `preferred_username` as the username claim), from the Camunda 8.10 properties reference, the same settings as a self-managed Camunda. It reaches the Keycloak over https trusting the test authority, through the Java truststore. Ready, without a token, is `/v2/topology` answering 401: the API up and protected.
- **The worker gets the token in the names of three families:** the Camunda SDK (`CAMUNDA_AUTH_STRATEGY=OAUTH`, `CAMUNDA_OAUTH_URL`, `CAMUNDA_CLIENT_ID`, `CAMUNDA_CLIENT_SECRET`, `CAMUNDA_TOKEN_AUDIENCE`, from the `Camunda.Orchestration.Sdk` README); the Camunda Spring SDK (`CAMUNDA_CLIENT_AUTH_METHOD=oidc`, `CAMUNDA_CLIENT_AUTH_TOKENURL`, `CAMUNDA_CLIENT_AUTH_CLIENTID`, `CAMUNDA_CLIENT_AUTH_CLIENTSECRET`, `CAMUNDA_CLIENT_AUTH_AUDIENCE`, `CAMUNDA_CLIENT_RESTADDRESS` and `CAMUNDA_CLIENT_GRPCADDRESS`, the `camunda.client.auth.*` and `camunda.client.*-address` properties in Spring's environment form, without the hyphens); and the older Zeebe Java client (`ZEEBE_CLIENT_ID`, `ZEEBE_CLIENT_SECRET`, `ZEEBE_AUTHORIZATION_SERVER_URL`, `ZEEBE_TOKEN_AUDIENCE`). A worker that reads other names uses `${camunda.tokenUrl}`, `${camunda.clientId}`, `${camunda.clientSecret}` and `${camunda.audience}`.
- **The test's own client** asks the same Keycloak for its token, on the Keycloak's mapped port, as `xunitassured-test`, and trusts only the test authority.
- **The names `keycloak` and the clients `camunda` and `xunitassured-test` are reserved in the oauth mode.** A container or a worker's client with one of them is a configuration error.
- **Outside the oauth mode, an OAuth placeholder is a configuration error** (there is no token to point to), as a Basic placeholder already was in the none mode. Before, both said that OAuth "comes in 6.40.0".
- **Cost:** the Keycloak adds about a minute and some hundreds of MB to the start-up. Basic stays the default.
