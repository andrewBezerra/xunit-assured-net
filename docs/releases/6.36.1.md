Bug fix release in XUnitAssured.Kafka: the produce steps honour the caller's cancellation token, and a consume started before its topic exists waits for the topic. Upgrading from 6.36.0 requires no code changes.

- **A consume waits for a topic that does not exist yet** (#219). Since 5.0.2, the consume steps look the topic's partitions up once and failed at once when there were none. Now they look again, every 250 ms, until the step's `Timeout`, so a consume that starts before the producer creates the topic reads the message. The same goes for `KafkaBatchConsumeStep`. A topic that never appears fails as before, with "Topic '…' has no partitions. It probably does not exist on the broker.", but only once the timeout is up. The caller's token stops the wait.
- **The step's `Timeout` covers the wait for the topic too.** The deadline starts with the step, not after the partitions are assigned. Against a topic that exists, this adds nothing worth measuring.
- **The produce steps honour the caller's cancellation token** (#218). `KafkaProduceStep` and `KafkaBatchProduceStep` link it to the step timeout:
  - a step started with a token that is already cancelled sends nothing;
  - a step cancelled while it waits for the broker stops there.
  
  Both report a failure with the `OperationCanceledException`, as the consume steps and the RabbitMQ publish do, and not a produce timeout. Before, the produce ran on a token of its own, made only from the timeout.
